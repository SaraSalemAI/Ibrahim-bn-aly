Design specification · Cedar Ridge Supply Co. (fictional)

Daily Finance Control Automation

A daily control that validates finance input files, recalculates the numbers, flags duplicate invoices, approval gaps and bank-to-ledger differences, and hands each exception to a named reviewer. All company names, people, addresses and amounts are invented.

00What is real today

The control logic is written and tested locally. Nothing runs on its own, and nothing is sent to anyone.

CapabilityStatusDetail

02Architecture

The runner reads and reports. It never changes a system of record. Anything that moves money or changes the books goes through a human approval step run by a different identity.

04Trigger

Schedule

Cron 15 7 * * 1-5 in America/Chicago. The scheduler passes the previous business day. If files are missing, validation fails and on-call is alerted.

File arrival

A storage event fires only in the approved folder and only for allowed senders. The source system writes all files and the manifest, then _READY last. A 09:00 check alerts if no run completed.

The business-date and holiday-calendar logic lives in the scheduler wrapper, so the runner gives the same result for the same date.

Integrations

  • ERP exports AP invoices, approvals and ledger cash entries as CSV with a manifest of fingerprints, row counts and control totals.
  • Bank statements arrive by SFTP (BAI2 or camt.053) and a normaliser script converts them to CSV with a manifest.
  • Notification service reads the outbox and must ignore repeats of the same routing key.
  • Approval workflow creates one task per action key. A separate identity executes approved actions in the ERP.

DUP-EXACTSame vendor and normalised invoice number more than oncePayment hold on later invoices

APR-MISSINGAmount ≥ 2,500.00 with no approvalBlock from payment run
SOD-SELF-APPROVALOnly approval is by the submitter. Always high severity.Block from payment run
APR-LIMITNo independent approver has a high enough limitBlock from payment run
REC-AMOUNTReference in bank and ledger with different amountsInvestigate and correct
REC-BANK-ONLYBank movement with no ledger entryJournal entry to record
REC-GL-ONLYLedger entry with no bank movement that dayInvestigate or carry as reconciling item

Severity is high when the amount is at least 10,000.00 or the rule is segregation of duties, low under 100.00, otherwise medium.

07Rerun safety

MechanismKeyEffect
Batch ledgerBusiness date + all file fingerprintsSame files run again are skipped. Nothing is written or routed.
Forced recompute--reprocessOutputs rebuilt. Routing and approvals stay deduplicated.
Exception IDDate + rule + record IDsA corrected batch keeps the same IDs for unchanged exceptions.
Routing keyException ID + recipientNo reviewer is notified twice about the same exception. A corrected batch still sends a fresh CFO summary.
Action keyException ID + proposed actionThe same action is never queued twice.
Run lockExclusive lock file or leaseTwo triggers cannot run at once. The second exits 3.

Remaining risk: drafts are written before the ledger is saved. A crash between the two can repeat drafts on a forced recompute, so the delivery and approval services must ignore repeated keys. Production should use a transactional store.

10Human approval for material actions

  • The runner never executes an action. Every proposal is queued as pending.
  • Non-material actions need one approver from the category's reviewer group.
  • Material actions (10,000.00 or more) need the category reviewer and the controller.
  • Approver, invoice submitter and executor must be different people or identities.
  • Changes to thresholds, routing or rules go through a pull request with a second reviewer.

11Deployment environment

  • Python 3.10 or later, standard library only. Tested on 3.13.
  • Three environments: dev with synthetic data, test running real triggers and delivery to a test mailbox, and prod.
  • One config file per environment under version control. Secrets come only from managed identity and the secret store.
  • CI runs the unit tests on every change and blocks merges on failure.
  • Separate landing, output, ledger and log storage per environment. Retention follows the finance records policy, for example 7 years.

12Who does what

Claude can do

  • Write and revise this design, the rules, config and schemas
  • Write and test the runner and its tests (done, on fictional data)
  • Run the runner on demand on files supplied in a session and explain results
  • Review a register or CFO summary and draft reviewer notes
  • Draft notification wording, runbooks and checklists

Claude cannot do on its own

  • Run on a schedule or react to file arrivals unattended
  • Hold production credentials or connect to the ERP or bank
  • Send notifications as part of this design
  • Approve, execute or post any financial action
  • Act as the system of record for the ledger or audit trail

Needs scripts

  • daily_control.py runner: written and tested
  • Bank file normaliser: not written
  • Scheduler wrapper with holiday calendar: not written
  • Transactional ledger adapter: not written

Needs external services or people

  • Scheduler or storage-event trigger, container runtime
  • Write-once storage, secret store, monitoring and alerts
  • Notification delivery and approval workflow
  • ERP and bank export jobs
  • Reviewers, controller, CFO, systems admin, internal audit sign-off

13Go-live gates

Each capability stays "designed but not active" until its gate is configured, tested and evidenced.

  • Source-system manifest export built and validated against the config
  • Bank normaliser written, tested and reconciled to statement totals
  • Runner image built in CI with tests green
  • Identities and permissions created exactly as in section 09, access review recorded
  • Write-once retention, ledger store and lock verified in test
  • Trigger configured in test and seen firing; duplicate-trigger drill passes
  • Delivery service configured; test message received; resend drill shows no duplicates
  • Approval workflow configured; material item requires two approvers; executor rejects unapproved keys
  • Alerts fire for run failure, validation failure and a missing successful run
  • Parallel run against the manual control completed and signed off by internal audit
  • Production enablement change approved

14Known limitations

  • Single currency (USD). Multi-currency needs validated FX rates as an input.
  • Fuzzy duplicate rule uses amount and date window only.
  • Reconciliation matches by reference on the business date only. Prior-day timing differences are not carried forward yet.
  • The file-based ledger and lock suit a single runner instance. A stale lock after a hard kill must be cleared by hand.
